Development Process

How PR Monitor Was Built

A step-by-step journey from a tester's problem to a working macOS tool — using Claude Code as a pair programmer, one pull request at a time.

Trigger — The Problem
As a tester, I needed to always watch PRs and CI jobs across multiple repos — without opening a browser tab every five minutes.
My Role
Tester. Responsible for catching what slips through — broken builds, unreviewed PRs, silent CI failures before they become incidents.
Claude Code
Personal subscription. AI pair programmer living in the terminal. Not a service — a collaborator. Used for the entire build: architecture, code, fixes, design.
The Goal
Learn new languages. Write structured, quality code I could read and maintain. Something organised — not just working, but well built.
Stack — Suggested by Claude
Claude recommended this combination for structure, learnability, and code quality. Each choice has a reason.
Electron React TypeScript (strict) Primer React GitHub GraphQL API GitHub CLI
Guardrails & Boundaries
📄 CLAUDE.md — project standards and rules committed directly to the repo. TypeScript, styling, error handling, file conventions.
🎯 Clear, scoped prompts — the more precise the instruction, the better the output. No vague asks.
🚧 No predefined agents — just prompts with explicit context and intent. Simple and controllable.
🔒 Defined scope — CLAUDE.md is explicit about what to build and, equally important, what NOT to build.
Development Loop — One Small Piece at a Time
Each feature or fix is a focused, independent unit. Never multiple concerns in one go — always one clear goal per session.

→

Design Iterations
Primer color tokens, PR row structure, section layout, header icons, mock window fidelity — refined across multiple sessions, always referencing the actual component code.
Bug Fixes
CI run deduplication (by startedAt), filter toggle, dynamic GitHub host detection, section renames. Each fixed in its own dedicated PR.
